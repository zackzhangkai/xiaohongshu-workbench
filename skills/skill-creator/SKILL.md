# skill-creator：创建与改进技能

好技能 = 把"你每次都要重复交代的要求"变成一次配置。本技能指导如何为本工作台编写和维护技能包。

## 本工作台的技能格式（真实契约）

```
skills/<技能id>/
  SKILL.md          # 必需：frontmatter + 正文
  references/       # 可选：资料文件（md/txt/yaml/json），加载时一并拼进提示词
```

`SKILL.md` 的 frontmatter 只有三字段生效：

```yaml
---
name: 技能id
description: |
  一句话职能。
  触发：用户会怎么说、什么时候用。
contextNote: 给系统的一句话边界（列表兜底展示用）。
---
```

- 技能 id 即目录名，对话里 `@` 选用；`description` 是用户在技能列表里看到的全部内容——写不好等于不存在。
- 单文件上限 120KB；大资料放 `references/`，主文件保持可读。
- 正文没有任何固定 schema，但它会**整体注入对话**——每一行都在消耗注意力，宁短勿全。

## 设计方法

1. **先找重复**：值得做成技能的任务满足两点——你会反复做（每周至少一次）、每次的要求稳定（不是"看心情"）。
2. **一句话职能**：填空"当用户说___时，按___方法产出___"。填不出来就还不该建。
3. **写正文四件套**：
   - 角色：一两句，说清它是什么、不是什么
   - 流程：编号步骤，每步一个动作，可执行可检验
   - 硬边界：绝不做的事（防跑偏比教能力更重要）
   - 输出格式：交付物长什么样，最好给标注式样例
4. **触发描述要双向**：写清"什么时候用"，也写清"什么时候不用"（"单张图请求不适用"这类排除句能挡掉一半误触发）。
5. **references 的用法**：正文放流程，references 放资料库（公式库、清单、模板）——流程稳定而资料常更新时，分开维护。

## 检验与迭代

- **上线即测**：用真实任务跑一遍，检查三件事——该触发时触发了吗、流程照做了吗、输出格式稳定吗。
- **记录失灵**：技能没被选中、选错、步骤被跳过，各记一条案例；两次同类失灵就该改描述或流程。
- **瘦身优先**：技能越用越肥是常态——每季度删一次"从没被遵循过的规则"，它们只是噪音。
- 版本对比：改进前先留旧版，同一真实任务各跑一遍，留效果好的那个。

## 反模式

- ❌ 写成产品说明书（技能指导"怎么做"，不介绍功能）
- ❌ 规则堆砌没有优先级（冲突时模型只能瞎猜）
- ❌ 一个技能管多类任务（拆）
- ❌ 触发词只有技能名（用户不会说"请使用 xx 技能"，要写自然语言触发）
